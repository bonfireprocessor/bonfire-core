# Agent Language Policy

## Speaking Language Restriction

This agent MUST respond exclusively in **German** or **English**. Responses in any other languages (e.g., French, Spanish, Chinese, Japanese, etc.) are strictly prohibited.

### Documentation and Code Language Rules

- **README files**: MUST be written in English only
- **Source code**: All comments, docstrings, and variable names MUST use English terminology
- **Code comments**: Never write technical documentation or comments in German - use English
- **Error messages**: Use English for all error handling and user-facing text
- **Configuration files**: Comments should be in English

> Exception: Conversational responses may be in German (or English), following the Speaking Language Restriction above.

## Coding Task Protocol

### Prioritizing Copilot Instructions

When performing coding tasks, this agent MUST also consult and follow the guidelines documented in:

1. `.github/copilot-instructions.md` - Coding standards, conventions, and technical requirements
2. `naming.md` - Naming conventions for identifiers, modules, tests, and artifacts

These files take precedence over general language policies for:

- Code style and formatting (copilot-instructions.md)
- Architecture patterns and design decisions (copilot-instructions.md)
- Testing strategies and coverage requirements (copilot-instructions.md)
- Security best practices (copilot-instructions.md)
- Project-specific APIs and interfaces (copilot-instructions.md)
- Identifier naming: variables, functions, classes, modules, tests (naming.md)
- File and directory structure conventions (naming.md)
- Versioning and semantic versioning schemes (naming.md)

### Conflict Resolution

If either `.github/copilot-instructions.md` or `naming.md` contains conflicting directives with this file's policies:
1. Technical coding standards in Copilot instructions take precedence (for code-related matters)
2. Naming conventions in naming.md are mandatory for identifiers, files, and documentation structures
3. Language for conversational responses follows this file (German/English only)
4. README files and code comments should still follow the language rules of this file

### Tooling Failure Policy

If required tooling or dependencies are missing, broken, or unusable (for example MyHDL, GHDL, conversion tools, or synthesis tools), the agent MUST stop and ask the user how to proceed. It MUST NOT autonomously install, repair, upgrade, downgrade, reconfigure, replace, or work around the affected tooling or environment.

### Integration Example

When receiving a coding task:
1. **Step 1:** Review `.github/copilot-instructions.md` for relevant guidelines
2. **Step 2:** Apply project-specific conventions documented there
3. **Step 3:** Write code comments and documentation in English (per this file)
4. **Step 4:** Communicate with the user in German or English (per Speaking Language Restriction)

### Examples of Correct Usage

✅ Correct:
- README.md written in English
- Comment in code: `# Calculate checksum for payload`
- Error message: `"Invalid input parameter provided"`
- User response in conversation: German or English (whichever the user prefers)

❌ Incorrect:
- README.md with German documentation
- Code comment: `# Berechne Prüfsumme für die Payload`
- Error message: `"Ungültiger Eingabeparameter"`

### Implementation Notes

- When users communicate in German → respond in German
- When users communicate in English → respond in English  
- When users communicate in another language → politely request communication in German or English, then respond in one of those two languages
- Never auto-translate responses to other languages
- Never mix multiple languages within a single response

### Rationale

This policy ensures clear and consistent communication with the user, who has specified a preference for these two languages. It also helps maintain clarity and avoid potential misunderstandings that could arise from using unapproved languages.

## Implementation Plans Location Policy

### Plan File Requirements

All implementation plans, migration strategies, and architectural documentation MUST be created in:
- **Directory:** `.agents/pi/plan/` (relative to project root; intentionally ignored by Git)

### Required Planning Content

Before implementing RTL or its testbench, the plan MUST cover all applicable bundle classes and interfaces, synchronous logic, combinational logic, testbench structure, directed test cases, and staged simulation/conversion/GHDL/synthesis verification. Implementation MUST NOT begin before the plan exists.

### Language Requirement for All Plan Files

**CRITICAL RULE:** ALL plan files MUST be written in English, regardless of the prompt language.

Even when a user requests plans or technical documentation in German, all plan files must be:
- Written entirely in English
- Use proper English grammar and spelling
- Avoid code-switching between languages

This applies to:
- Implementation planning documents (e.g., `migration_plan.md`, `architecture_decision.md`)
- Technical specifications within plans
- Rationale and reasoning sections
- Test strategies and validation approaches

> **Never** write implementation plans in German, even if the user prompt was in German.

### Correct vs Incorrect Examples

✅ CORRECT (English plan file from German prompt):
```markdown
# Cache Unit Tests Migration Plan

## Background
The legacy runner `tb_run.py` contained cache unit tests...
```

❌ INCORRECT (German content in English file):
```markdown
# Cache Test Migrationsplan

## Hintergrund  
Der Legacy Runner enthielt Cache-Tests...
```
